Vibecoding workshop · Part 1 05 / NN

Part 1 · Iteration

Now tell it what's wrong.

You don't edit the code, you say what you want instead. Pick whichever of these your version needs, or invent your own.

Make it live

"Make the total tick up live while the meeting runs, with Start, Pause and Reset buttons."

Make it look better

"Make this a dark-mode dashboard with one big headline number."

Make it honest

"Assume an 1,800-hour working year, and show me the assumption on screen."

Make it easier

"Let me pick a salary band from a dropdown instead of typing a number."

Make it sting

"Underneath, tell me what else that money could have bought."

Make it useful

"Add a button that copies a one-line summary I can paste into an email."

Ask for one thing at a time. If you stack five changes into a sentence you'll get four of them and no idea which one it dropped.

Vibecoding workshop · Part 2 09 / NN

Part 2 · Open this on the projector

One question, one answer.

The question we're asking: is there a place called Tokyo, and if so, where exactly is it? That question is the web address. The answer comes back as text.

https://geocoding-api.open-meteo.com/v1/search?name=Tokyo&count=1

{ "results": [ {
    "name": "Tokyo",
    "country": "Japan",
    "country_code": "JP",
    "population": 9733276,
    "timezone": "Asia/Tokyo",
    "latitude": 35.6895,
    "longitude": 139.69171
} ] }

What you're looking at

  • "country": "Japan"Words in quote marks are text. Your app can print this straight onto the page.
  • "country_code": "JP"Two letters, which is all you need to fetch the right flag image.
  • "population": 9733276No quote marks, so it's a number. Your app can do maths with it.
  • "latitude" / "longitude"Coordinates. Hand these to a weather API and you've joined two sources together.

Nobody is meant to read this. It's ugly for us and trivial for an app, which is the whole point. Every project this afternoon starts by opening a web address like this one and seeing what comes back.

Vibecoding workshop · Part 2 10 / NN

Part 2 · Before you plug anything in

The easy ones, and the others.

Everything in today's list is free and keyless: no sign-up, no password, safe to use straight away. Out in the wild, some APIs ask for more. Three things to know.

  • 01

    Some APIs need a key, and a key is yours alone

    A key is a password an API gives you when you register with it. They exist mostly so nobody can abuse or overload the service, and so usage can be traced back to whoever signed up. That person is you. Share it and someone else can run up your bill, or get you cut off.

    Never

    Give your key to Gemini, or let it write the key into the code. Anyone who opens the app can pull it back out.

    Instead

    Ask Gemini to have the app request the key from whoever is using it, so it's typed in fresh and never stored.

  • 02

    Rate limits and CORS

    Free endpoints cap how many requests they'll answer, so thirty people hammering the same one can trip a shared limit. Spreading out across different APIs keeps everyone's apps working. Some APIs won't talk to a browser at all. If you're not sure what one will and won't do, ask Gemini to explain the API's limits and what you can build with it before you start.

  • 03

    A public link is public

    The share link you'll generate at the end is readable by anyone who has it. Perfect for a weather app. Never for anything carrying internal or sensitive data. We'll come back to this before you share.

Vibecoding workshop · Part 3 16 / NN

Part 3 · Debugging, on purpose

Now type Newcastle.

It breaks. Reliably. Which makes it the most useful thing on this slide.

What you type What comes back
Tokyo Japan, 9.7 million, a flag and a photograph. Perfect.
Reykjavík Iceland. The accent survives the round trip.
Newcastle Open-Meteo confidently says Australia. Wikipedia hands back a disambiguation page with no photo and a useless paragraph.

Two sources, quietly disagreeing. Fix it live by asking for the region to be added to the Wikipedia lookup. Then say the useful thing out loud: your app is only ever as careful as the questions you ask of it.

Vibecoding workshop · Part 4 23 / NN

Part 4 · Leave this up

Definition of done

You have a page that pulls live data from the internet and shows it on screen. Everything beyond that is bonus.

When it breaks, paste this

This isn't working and I see this error: [PASTE THE RED CONSOLE TEXT]. Explain what's wrong in plain English, and give me the complete corrected file - no snippets.

Where the red text lives

  1. F12, then click Console
  2. Or right-click the page, then Inspect, then Console
  3. Read the first red line. It's usually a typo in the URL, or CORS

Part 5 · Three ways up

Pick a rung.

In order of ambition. The first one is the one that matters.

  1. 01

    Add the brain

    If you haven't already, this is the big one. Send your data to Gemini and ask it to summarise, rewrite, classify or advise.

    "Send this to Gemini and ask it to explain what it means in three bullets, in plain English."

  2. 02

    Refine by conversation

    Iterate on look and feel. You are allowed to be fussy. It costs you a sentence.

    "Make this a dark-mode dashboard." · "Move the result box to the top." · "Can it show three cities at once instead of one?"

  3. 03

    Chain a third source, or find your own

    For the confident. Run the discovery prompts and wire in something genuinely new, or feed one API's output into another.

    "Take the coordinates from this response and feed them into Open-Meteo to show the weather there too."

Vibecoding workshop · Part 6 27 / NN

Part 6 · Before you send anyone a link

Share it. But read this first.

How

Public Share Link

Generate one from Canvas and put it on the main screen. It works on anyone's phone, with no install and no account. That's genuinely useful, and it's why people will ask you for it.

The catch

Public means public

Anyone with the link can read it. Perfect for a weather app. Never for anything containing internal or sensitive data. This is rule 03 from the start of the session, arriving exactly when it matters.

Vibecoding workshop · Part 6 28 / NN

Part 6 · What to take away

Six things worth keeping.

  1. 01
    Live data is the step that turns a toy into something usefulEverything before that is a nice demo
  2. 02
    Finding good APIs is easy. Keys, CORS and rate limits are the hard partAnd they're the part nobody warns you about
  3. 03
    You no longer need to know syntax to build data-driven toolsYou need to know what you want
  4. 04
    How data moves now matters more than where the semicolons goJSON, arrays, objects. That's the literacy
  5. 05
    The real leap is the handoffStructured data from an API, plus a model's reasoning. That pattern generalises to almost any task in any department
  6. 06
    Prototypes built here export cleanlyWhen something's worth scaling, it moves to a secure environment with proper keys
